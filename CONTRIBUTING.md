# Contributing to foliot

A planned orchestrator for coding agents.

foliot has one maintainer, Abhijeet Halder, and changes are proposed as pull requests against `main`.
Open an issue before starting anything larger than a small fix.
Agreeing on the approach in an issue costs far less than a pull request that has to be turned down.

## Where this project's own rules live

`README.md` says what foliot is and how to use it.
`AGENTS.md` says how to build it, how to run its checks, and which rules a change to this project is held to.
Those rules differ from one project to the next, so they live there and not in this file.
Read both before writing code.

## What every change needs

- **A test that failed before the change and passes after it.** Paste both runs in the pull request, because a test that was never red has not shown that it tests anything.
- **The checks `AGENTS.md` names, passing on your machine** before you push.
- **One logical change per pull request**, small enough to read in one sitting.
- **Commit messages in [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) form**: a type such as `feat`, `fix` or `docs`, then an imperative subject of at most 72 characters with no trailing period.
- **No `Co-authored-by:` trailer for a tool or an agent.** Credit people.
- **No machine-detectable origin marks.** No invisible or zero-width characters, no hidden markers, no "generated by" tags. A source a reader can follow is welcome; a signal planted for a detector is not.

## Writing the pull request

Say what the change is for, what changed, and how you tested it.
Paste the test runner's own output instead of summarising it.
If you turned down an obvious alternative, name it and give the reason.

## Security problems

A vulnerability is never reported in a pull request or anywhere public.
[SECURITY.md](SECURITY.md) gives the one route for it.
